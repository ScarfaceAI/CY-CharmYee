# 承意下一阶段方案：本地识别、知识与决策、创作者工具

状态：**方案已确认，第一期实施中**。依据是 2026-11-16 的四轮问答（Q1–Q30），以及当天对代码、模型许可和运行环境的核对。第一期的试跑已完成，结论见「第一期 → 试跑结论」。实现后另写验证记录；这里的计划不能当作已验证的结论。

## 一句话说清楚

承意要从“帮抖音创作者转文字的工具”，变成“在你电脑上运行的个人知识与决策伙伴”：

> 承意：在你电脑上运行的个人知识与决策伙伴，把你看到、听到、经历的变成随时能查的资料，做决定时调出相关依据，事后陪你复盘。

“承你所想，会你所意”保留作口号。处理视频和文稿降为“资料的入口之一”。分三期交付，每期单独发版：

| 阶段 | 做完后最直接的感受 | 计划版本 |
| --- | --- | --- |
| 一「识别与日常」 | 不用申请 Key，也不花钱，识别在本机跑；一条命令出稿；错字会被标出来；该提醒的事程序自己说 | 2.0.0 |
| 二「知识与决策」 | 记下重要决定，到期提醒复盘；做新决定时调出相关的旧决定和资料；转写稿和知识库一起搜 | 2.1.0 |
| 三「创作者工具」 | 找出账号里的爆款并对比差在哪；学结构不抄表达；追踪对标；选题池；支持 B 站和 YouTube | 2.2.0 |

第一期去掉豆包，安装和配置方式都变了，属于不兼容的大改，所以主版本号升到 2。

## 三条原则

1. **资料留在本机。** 识别换成本地模型后，承意不再上传你的音频、文稿和资料；联网只用来下载视频和模型、检查更新。你和 Agent 的对话，包括 Agent 读到的稿子和资料，按 Agent 服务商的规则处理。这一点在首页如实写明，不说“完全本地”。
2. **错了能被发现，不假装不会错。** 本地模型和豆包一样会出错，难办的是错得像真的，比如“小王”听成“小汪”、“700”听成“7000”。所以每份稿子附疑点清单；校对只改有依据的地方，并列出改动；默认参数由测试数据决定。
3. **该说的话由程序保证。** 更新提醒、到期复盘、获取失败时的退路，都由程序写进输出里的 `tell_user` 字段，Agent 原样转告。规则文档只留必做项。

## 借鉴了哪些行业的做法

| 承意的问题 | 别的行业怎么做 | 借过来的做法 |

| 同音错字，读着通顺，校对时看不出来 | 输入法：同一个拼音有多个候选，结合上下文和你的用词习惯来选 | 稿子里和词库词“拼音相同、字不同”的地方标成疑点，附上候选 |
| 人名术语每次都认错 | 速记员开庭前按案卷准备专用词典；翻译软件的术语库和翻译记忆 | 每条视频按标题、话题、账号挑一份专用热词；校对改过的地方攒成纠错记忆 |
| 越改越错 | 摄影的 RAW 与非破坏性编辑：原片永远保留，调整随时可撤 | 模型原始输出原样保留；数字转换、热词、校对都是叠在上面的层，可关、可重算 |

| 大文件从哪下、可不可信 | 软件包管理器按文件哈希认文件，换哪个镜像都行 | 模型清单写死 SHA-256，国内镜像、GitHub 哪个能用用哪个，对不上就不用 |
| 后台任务拖慢电脑 | 备份软件、系统更新在后台低优先级运行 | 识别默认只用一半 CPU 核心、最多 4 个线程，低优先级运行 |
| 规则太多，Agent 记不住 | 丰田的防错设计；航空检查单只留致命项 | 程序返回 `tell_user`；规则只留必做项 |
| 转一条链接要 8～10 步 | 平台工程的“铺好的路” | `quick <链接或文件>` 一条命令 |
| 抖音改版了，任务失败才发现 | 网站运维的定时探测与熔断 | `selftest` 用固定样本探测，坏掉的通道往后排 |
| 决定做完就忘 | 军队的事后复盘、投资人的决策日志 | 决定前写下预期，到期对照实际 |
| 两份“你是谁” | 企业主数据管理只认一份正本 | 个人画像以「个人助手」为准，承意只读 |
| 判断哪条是爆款 | YouTube 分析工具的“离群分” | 拿作品和账号自己的中位数比 |
| 改写有洗稿风险 | 著作权“思想不保护、表达才保护”；论文查重 | 只学结构，写完算和原文的重合率 |
| 该支持哪些 Agent | Rust、Python 给平台分级 | 一级在真实对话里验收，其余社区支持 |

### 试跑结论（2026-11-16）

在作者的电脑（6 核 12 线程、32 GB 内存）上，用已有的 7 条校对稿（277 秒，1155 字）实测。这是体检，不是正式基准。

| 项目 | 结果 | 对方案的影响 |
| --- | --- | --- |
| 安装 | sherpa-onnx 2.0.1 在 Windows、Python 3.12 上直接装好，CPU 版不需要 PyTorch | 依赖定为 sherpa-onnx、sherpa-onnx-core、numpy、pypinyin，版本钉死 |
| 速度 | Qwen3-ASR 用 3 个线程，处理时间约为音频时长的 0.17 倍：10 分钟视频约 1.7 分钟，2 小时录音约 21 分钟。FireRed 慢约 1.85 倍 | 默认 3 个线程；后台运行的门槛不变 |
| 内存 | Qwen 峰值约 2.5 GB（提交内存约 3.7 GB）；FireRed 约 1.7 GB | 最低配置写 8 GB 内存 |
| 错字率 | 7 条合计：Qwen 7.10%，FireRed 6.67%，豆包 4.76%。去掉粤语口音那条后，6 条普通话：Qwen 4.61%，FireRed 4.42%，豆包 2.26% | 普通话上本地模型约是豆包的 2 倍，超过 1.5 倍的线。样本太小，以正式基准为准；正式基准也超线的话，按方案不删豆包，先把差距和选项摆给你 |
| 标点 | Qwen 自带标点；FireRed 没有，配标点要用 PyTorch 模型，违反 Q24 | **接入只做 Qwen3-ASR**；FireRed 只在正式基准里当参照 |
| 热词 | Qwen 可以给每一段单独设热词，不用重新加载模型；示例里 31 处错修到 20 处，同时把 2 处原本对的改错了。FireRed 不支持热词 | 两遍对照的做法可行而且便宜；副作用确实存在，疑点层必须有 |
| 断句 | VAD 设的 20 秒最长时长只是软限制，实际出现 22 秒的段 | 超长的段由我们自己硬切到 15 秒以内 |
| 编造 | 30 秒静音和 30 秒低音量白噪声，VAD 一段都没放行，输出 0 字 | 音乐素材仍待测 |
| 下载 | 从这台电脑看，GitHub、ModelScope、hf-mirror、Hugging Face 都能下，Qwen 各源文件哈希一致；Silero VAD 在 GitHub 和 Hugging Face 上是两个不同的文件 | 清单按文件哈希锁定，Silero 锁 GitHub 版；国内其他网络环境仍待验证 |
| 许可 | sherpa-onnx、Qwen3-ASR、FireRedASR2 上游是 Apache-2.0，Silero VAD 和 pypinyin 是 MIT；sherpa 转换后的模型包里没有 LICENSE 文件，Qwen 的转换者（ModelScope 上的 zengshuishui/Qwen3-ASR-onnx）声明 Apache-2.0 | THIRD_PARTY_NOTICES 写清上游和转换者两层出处 |
| 显卡 | 只查了资料：Windows 显卡版要另装 CUDA 运行库，合计约多下载 1.5～1.65 GB；int8 模型在显卡上能快多少没有把握 | 2.0.0 不含显卡附加项；等你用过 CPU 版的实际速度再决定要不要实测 |

### 改哪些地方、复用什么

**本地识别**

- 新增 `scripts/runtime/douyin_text/local_asr.py`：用 sherpa-onnx 加载识别模型，用 Silero VAD 断句。VAD 是一个小模型，判断哪里有人说话，并按停顿切成一句句。
  - 输入沿用 `media.extract` 切好的分片。`media.py` 已经用 ffmpeg 生成并校验 16 kHz 单声道 WAV，正好是本地模型要的格式。
  - 输出沿用现有结构：全文，加上每句的起止时间。所以普通字幕、校对版字幕和续做都不用改。
- 识别在单独的子进程里跑，低优先级、限线程。取消做法复用 `processes.py` 现有的“只管自己的子进程树”。同一台电脑同一时间只跑一个识别，其他排队，免得几个对话一起把 CPU 占满。
- 新增 `scripts/runtime/douyin_text/models.py` 和模型清单 `assets/models.json`：
  - 清单里每个模型写明下载地址（可以有多个镜像）、大小、SHA-256 和许可。
  - 下载前检查磁盘空间，支持断点续传；哈希对不上的文件不用。
  - 下载在后台进行，命令立即返回，可以随时查进度。1 GB 在慢网速下可能要十几分钟，会超过 Agent 单条命令的时间限制。
  - 没网或下不动时，可以手动下载，再用 `models import` 导入，同样校验哈希。
  - 缓存默认在 `%LOCALAPPDATA%\cy-charmyee\models`，几个工作区和以后的版本共用；可以改到别的盘。
- `workflow.py` 的 `transcribe` 改为调用本地引擎。豆包那套“付费请求失败或结果未知时，先核对再明确重试”的状态，简化为“没跑完的分片自动重跑”；已完成的分片照样复用。
- **旧任务兼容（核对代码时发现的硬风险）**：
  - 现在的识别结果存在 `outputs/<作品>/<豆包参数哈希>/` 下面，目录名来自全局的 `asr.PROFILE`（`workflow.version_for`）。换引擎后哈希会变，旧任务会找不到自己的稿子，甚至被重新识别。
  - 改法：每个任务记下自己用的识别档案，旧任务继续读原来的豆包结果；只有你明确要求重新识别时，才用本地模型另存一个版本。
  - `continuation.py`、`creator.py` 里用到 `version_for` 和 `asr.PROFILE` 的地方一起改。
- `doctor` 不再检查豆包 Key，改为检查模型是否就绪、磁盘空间和可用线程。

**显卡（Q25）**

- 默认只用 CPU：线程数取物理核心的一半，最多 4 个，低优先级。试跑实测：3 个线程时，处理时间约为音频时长的 0.17 倍。
- 显卡做成可选的附加项，默认不装，2.0.0 先不做。sherpa-onnx 的 Windows 显卡版不在 PyPI 上，要另装它的 CUDA 版本和 CUDA 运行库，试跑查到合计约多下载 1.5～1.65 GB；DirectML 版要自己编译。
- 以后要做，必须同时满足以下几条，达不到就不提供，验证记录里写明实测数字：
  - 长录音至少比 CPU 快一倍；
  - 显存占用不超过 2 GB；
  - 额外下载多大，装之前告诉你，你同意才装。
- 装了显卡版却跑不起来时，自动退回 CPU。

**纠错层**

- 新增 `numbers.py`，做保守的数字转换，口径参照 GB/T 15835-2011：
  - 只转数量加单位、年份、百分比、比分、型号里的数字。数量统一一条线：小于 10 的整数保持汉字（“一个人”“两次”“有一天”“三公里”），10 及以上或带小数的才转；“十到二十天”这类范围两端一起转或一起不转；
  - 英文旁边的数字后面跟着量词时按数量处理（“QQ 两次”“Claude 三天”不转），真正的型号才转（“AK47”“M4A1”“5G”）；
  - 成语、约数（三四个、十几个）、序数词（第一）、固定说法不动，拿不准的也不转；
  - 阿拉伯数字、英文与相邻汉字之间留一个空格，与你校对稿的写法一致（“616 宇宙”“手游 FPS 的上限”），可以单独关掉；
  - 转换只作用在展示稿上，模型原文另存。机器原稿和登记过的校对稿用哈希绑定，所以已生成的稿子不原地改写：关掉后，新识别的稿子不再转换；旧稿子用 `redisplay` 另存一个新版本，不用重新识别。
- 新增 `lexicon.py`，管理分层词库，并为每条视频挑词：
  - **公开词库**：THUOCL（清华开放中文词库），MIT 许可，11 类约 15.7 万词，2016–2017 年更新。第一次需要时自动在后台下载（约 2.7 MB）、校验，不进安装包。实测它是 IT、财经、地名、饮食、成语等领域词表，**没有通用词汇**（“激发”“元气”“对峙”都不在里面），所以只用来提供地名、人名、术语等专有名词候选，以及给数字转换提供成语例外。判断一个片段像不像常见词，用 jieba 0.42.1 的词典数据（MIT 许可，约 35 万词条、4.8 MB）：只下载词典文件，不装 jieba 程序包，同样第一次需要时在后台下载、校验，不进安装包。在 7 份校对稿上，它覆盖约 71% 的汉字位置，pypinyin 自带的词组表只有约 27%。只有和这条视频主题相关的词，才会当成热词送给模型。
  - **你的词库**：你手动加的词，你导入的词表（个人使用，不进仓库），以及从已登记的校对稿和知识库页面标题里学到的词。
  - **纠错记忆**：每次登记校对稿，自动比对“识别原文 → 校对稿”，把改动记下来，连同次数、出现在哪个账号或主题、有没有被否定过。确认得越多、越近、越相关，权重越高；同一个词你在某个场景里没改，它在这个场景的权重就降低。改动按词记，不按单字记；虚词、语气词、单字和纯增删只记录、不提示。含汉字的记忆默认只在同一账号或话题下提示（“激发”在别的视频里可能就是对的），在两个以上不同账号或话题里都确认过才全局提示；英文专名（WorkBuddy、QClaw）直接全局。纠错记忆只做提示，不自动替换（Q6）。明显的专有名词，Agent 可以直接加进你的词库，并注明来源。
  - **这条视频的上下文**：标题、话题标签、简介、账号名，以及这个账号过去的更正。
  - **每条视频怎么挑**：先按上下文判断主题，再从各层词库里挑出和这条视频相关的词，按相关程度排序，只把最相关的几十个送给模型，上限在测试里定。其余的词不送模型，只在识别完后用来找同音疑点。
  - **对冲热词副作用**：热词可能把对的改错。官方示例里，热词就把原本对的“自治州”改成了“自制粥”。所以可能受热词影响的句子，带热词和不带热词各识别一次；两遍结果不一样，就标成疑点，两种写法都给出。只重跑这些句子，不整条重跑。
  - 判断同音要先把汉字转成拼音，用 pypinyin 0.55.0（MIT 许可，约 3.3 MB）。只忽略声调，不放宽声母、韵母。
- **疑点清单**：单独存一个文件，不往稿子里插标记。疑点分几类：
  - 同音或近音；
  - 纠错记忆命中；
  - 热词前后两遍不一致；
  - 数字（全部列出，供核对）；
  - 疑似编造：静音或音乐段出了字，或者出现“请不吝点赞订阅”这类整句套话。

  疑点要少而准：只有识别出的片段本身不像常见词，而且和某个候选词拼音相同时，才标同音疑点。候选来自三处：
  - 你的词库和相关的纠错记忆；
  - 这条视频的标题、话题、简介、账号名，用通用词表切出 2～12 个字的词，只对这条视频有效，不写进你的词库（“#对峙2国服来了”切出“对峙”）；
  - 公开词库里的人名、地名、术语，只有在这条视频的上下文里原样出现才算，免得冷门人名到处误报。

  通用词表还没下好时，这一次不出同音疑点，清单里写明原因，同时在后台下载；其他几类照常。清单存为 `suspects.json` 和 `suspects.md`，记下对应稿子的指纹，稿子变了会提示重算；词库变了，用 `suspects <任务>` 重算，稿子本身不动。
- `content.py` 的 `register_content` 登记校对稿时，做三件事：算出改动清单（原文 → 改后），更新纠错记忆，在 `tell_user` 里告诉你改了几处。已经登记的 7 条校对稿，用来初始化纠错记忆。

### 关键取舍与边界

- **先试跑，再写正式代码。** sherpa-onnx 加 Qwen3-ASR 在 Windows、Python 3.12 上，没有人替我们验证过。第一步在独立的临时环境里跑通两个候选模型，实测速度、内存峰值、热词接口、VAD 断句长度、下载源和许可。已完成，各项都可行，结论见上方「试跑结论」。
- **验收不过怎么办。** 不删豆包。先把差距和选项摆给你：换模型、调热词，或者接受某项差距，由你定。
- **字幕条可能变长。** Qwen3-ASR 只给 VAD 断句的时间，没有逐字时间，字幕条可能比豆包的长。VAD 自带的最长时长只是软限制（试跑出现过 22 秒的段），所以超过 15 秒的段由我们自己再切开，再配合已有的 `--max-chars` 拆成短行。校对版字幕按数字转换后的文字对齐，照常可用。
- **编造。** 静音段由 VAD 挡住，不送进模型；音乐段可能被当成人声。用 3 段测试素材检查，剩下的风险由疑点清单兜住，不偷偷删掉。
- **中途取消或断电。** 分片逐个存盘，再跑时从没完成的分片继续。
- **磁盘和内存。** 模型约 1 GB，下载期间要预留约 2 倍空间。识别时的内存峰值在试跑中实测，写进最低配置说明。卸载说明里写明模型缓存的位置。
- **安全。** 模型文件只认清单里的 SHA-256；不执行任何下载来的代码；模型和词库不进 Release 包。
- **升级路径。** 已安装的用户用 `update --apply` 升级时，安装器会按新的依赖清单装上 sherpa-onnx。用隔离环境实测从 1.8.0 升级。
- **隐私说法。** 文档写“承意不上传你的音频、文稿和资料”，不写“完全离线”：下载视频、下载模型和检查更新仍然要联网。

### 验收

- **改代码时的快测**：只跑相关的测试文件，例如 `python -B -X utf8 -m unittest discover -s tests -p test_numbers.py`，几秒钟出结果。CI 不下载 1 GB 的模型，识别引擎用替身测流程；真实模型只在本机测，结果写进验证记录。
- **合并前**：在 Python 3.12、锁定依赖的环境里跑全量 `python -B -X utf8 -m unittest discover -s tests`，再加上 GitHub 的 Windows CI。
- **真实验收（决定能不能删豆包）**：
  - **素材**：已有的 7 条校对稿（合计约 4.6 分钟）算完整错字率；你补的 5～10 段（合计 30～60 分钟）只列人名、术语、数字；另有 3 段静音或纯音乐。7 条校对稿总共只有 1000 多字，整体错字率只能当参考，人名、数字、术语的对比更有分量。
  - **豆包对照**：7 条校对稿直接用当时的豆包原始结果，不再发请求。新素材需要再跑一次豆包，见文末“待确认”。
  - **算法**：比错字率前，统一去掉标点、统一数字写法。7 条校对稿是在豆包结果上改出来的，措辞天然偏向豆包，结论里会注明。
  - **不许“偷看答案”**：测某一条时，纠错记忆只能用其余几条的校对结果（留一法）；你列的词表只用来打分，不放进热词。否则成绩会虚高。
  - **通过线**：
    - 本地模型的原始错字率不高于豆包的 1.5 倍；
    - 纠正之后，人名、数字、术语的准确率不低于豆包的原始结果；
    - 静音段和纯音乐段一个字都不出；
    - 校对改对的地方多于改错的地方；
    - 数字转换和热词各自都要“修好的比改坏的多”，才默认打开。
  - **另外统计两个数**，不当通过线：漏网的关键错误（既没改对，也没标成疑点），以及疑点的命中率。
  - **其他实测**：
    - 在你的电脑上测速度；
    - 用你的 1～2 条视频跑 `selftest`；
    - 从 1.8.0 升级上来；
    - 在 Claude Code 和 Codex 里各跑一次真实对话，检查瘦身后的规则和 `tell_user`；
    - 字幕拖进剪映，由你看一眼效果。
  - 测试素材和逐条结果只留在你的工作区；仓库里的验证记录只写汇总数字。

- **敏感内容。** 决策可能涉及健康、财务和人际关系，全部只存在本机。搜索结果交给 Agent 时，只给命中的片段，不给整份文件。

### 验收

- 快测：`test_decisions.py`、`test_search.py` 等单个文件。
- 合并前：全量测试，加 Windows CI。
- 真实验收：
  - 在你的知识库里记 1 个决定，改日期模拟到期，走一遍复盘；
  - 在你实际的工作区建索引，测几个两字词和多字词查询的速度和结果；
  - 在 Claude Code 和 Codex 里各跑一次真实对话，看到期提醒有没有原样转告。

## 第三期「创作者工具」（2.2.0）

### 用户能看到的变化

- **爆款对比**：对一个分析过的账号，算出每条作品的数据是账号中位数的多少倍，列出明显高出的作品，再对比它们和普通作品在开头 15 秒、时长、语速上的差别。
- **学结构不抄表达**：把参考稿拆成结构（钩子 → 论点 → 例子 → 引导），你用自己的素材重写。写完自动算和原文的重合率，超过阈值就提醒，并标出重合的句子。
- **对标账号追踪**：维护一份对标清单，手动刷新，看新作品和新爆款。想定时刷新，就用 Agent 平台自己的定时功能，默认关闭。
- **选题池**：知识库里的一份 Markdown 清单。来源包括爆款对比、你的想法和决策记录；状态分待做、在做、已发。
- **B 站和 YouTube**：用已经装好的 yt-dlp 获取。平台有字幕就直接用，没有再本地识别。

### 改哪些地方、复用什么

- 爆款对比：复用 `creator.py` 的互动数据和指标，以及 `scripts/compare_text.py` 的时长和语速测量。
- 重合率：新增 `overlap.py`，按连续若干个字的片段比对，也就是查重常用的“片段指纹”。复用 `subtitles.py` 的切词规则，保证数字和英文不被拆开。
- 对标追踪和选题池：复用博主任务（`creator_cli.py`）和知识库写入（`personal_vault.py`）。
- 新平台：`media.py` 现在只认抖音链接和本地文件（报错原文是“当前仅支持抖音链接及本地音视频”），扩展到 B 站和 YouTube 链接。平台字幕转成和识别结果相同的结构。

### 本期不做

小红书、视频号、剪映草稿、自动发布、替你选题。

### 关键取舍与边界

- **比哪个数。** 抖音一般不公开别人作品的播放量，所以抖音以点赞为主、参考评论和转发；B 站、YouTube 用播放量。
- **数据是某一时刻的快照。** 爆款倍数注明获取时间。太新的作品（比如发布不到 3 天）单独标出，不和老作品直接比。
- **样本太少不算倍数。** 作品少于 10 条时，只列数据。
- **平台字幕不一定可靠。** 平台字幕可能是自动生成的，要标明来源。B 站的部分字幕要登录才能拿，YouTube 可能要求验证；拿不到就退回本地识别，不自动登录。
- **重合率只是提醒。** 它不判断是否侵权。

### 验收

- 快测：单个测试文件。
- 合并前：全量测试，加 CI。
- 真实验收：
  - 用一个真实账号跑一次爆款对比；
  - 用一篇参考稿走一遍“学结构 → 重写 → 算重合率”；
  - B 站和 YouTube 各测 1 条有字幕的、1 条没字幕的。

## 执行方式

- 每期一个工作分支，必要时拆成几个 PR，都经过 Windows CI 再合并到 `main`。发版用 `scripts/release.py` 预检，再用 `--publish` 发布，公开下载校验通过后报告版本号。
- 第一期按这个顺序做：
  1. 试跑；
  2. 接入本地识别，豆包暂时保留，方便对照；
  3. 纠错层；
  4. 基准测试，选定默认；
  5. 日常体验：`quick`、`tell_user`、规则瘦身、`selftest`；
  6. 撤豆包、只留中文、去掉费用功能；
  7. 发布 2.0.0。

  等你素材的这段时间不空等：先做不依赖素材的部分，第二期的代码也可以提前开工，但仍按顺序发版。
- 撤豆包和打包相关的改动风险最高，合并前单独做一次代码审查。
- 这份方案随第一期的第一个 PR 一起提交。实施中发现方案有错，先改方案，再改代码。

## 风险与待验证

| 风险 | 影响 | 怎么处理 |
| --- | --- | --- |
| 本地模型在普通话上的原始错字约是豆包的 2 倍（试跑小样本） | 过不了 1.5 倍的线，豆包就删不掉 | 以正式基准为准；纠错层要把人名、数字、术语补回来；还不行就把差距和选项摆给你 |

| 热词副作用 | 把对的改错 | 两遍对照，由测试决定默认 |
| 疑点清单在 7 段留一法里一处真错也没标出来（0／44） | 换到新账号时，纠错记忆和同音疑点暂时帮不上忙 | 44 处里约三分之一是校对时顺手删改的语气词和字词，12 处是粤语被认成普通话，其余多是新产品名，在别的账号里学不到。靠同一领域慢慢攒下的记忆、每条视频的热词和两遍对照来补，再查模型能不能给出每个字的把握程度；正式基准里单独统计漏网的错误 |
